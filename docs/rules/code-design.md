# 设计原则与抽象规范（Code Design）

> 配套：`docs/constitution.md#0-金线判准`、`docs/rules/quality-gates.md`。
> 用途：AI 设计 / 编写 / 审查代码时的设计期约束与诊断清单。
> 来源：高质量稳定代码的构建范式（金线原则）+ 业界 SOLID 诊断法 / 代码坏味道 / 契约设计。

## 1. 设计原则清单（每条配"审代码时这样问"）

原则不是口号，是审代码时的诊断问句。AI 在写码前、审码时，逐条用 Ask 自检。

### 1.1 SOLID
- **SRP 单一职责**
  - Ask：这个模块 / 类 / 函数的「唯一变更理由」是什么？超过 1 个变更理由 → 拆。
- **OCP 开闭**
  - Ask：加一种新情况，是改旧代码还是加新代码？应"对扩展开放、对修改关闭"。
- **LSP 里氏替换**
  - Ask：子类 / 实现能否无脑替换父类而不破坏调用方预期？不能 → 抽象错了。
- **ISP 接口隔离**
  - Ask：调用方是否被迫依赖它用不到的接口？是 → 拆小接口。
- **DIP 依赖倒置**
  - Ask：高层模块是否依赖了低层细节？应都依赖抽象（接口 / 纯函数），运行时注入。

### 1.2 通用原则
- **DRY 不重复**：Ask — 同一逻辑是否出现了两处以上？但注意 **DAMP > DRY**（测试/意图清晰的重复优于强行抽抽象）。
- **KISS 简单**：Ask — 是否存在更直白、代价更低的写法？不为"显得高级"引入复杂度。
- **YAGNI 不过建**：Ask — 这个功能现在真有人用吗？没明确需求就别预建（见 constitution 第 1 节）。
- **Tell-Don't-Ask**：Ask — 是"请对象做事"还是"撬开对象掏数据自己算"？后者是坏味道（Feature Envy 信号）。
- **Fail Fast 不吞错**：Ask — 出错时是立即暴露（抛/返回错误），还是默默吞掉继续跑？吞错埋雷，违反金线"可验证"。

## 2. 抽象与架构规则

- **抽象层级一致**：一个函数 / 一屏代码里，要么都在"业务意图"层，要么都在"实现细节"层，不混层（不要上层逻辑里突然插一行底层位运算）。
- **低耦合高内聚**：模块对外暴露的"表面积"尽量小；模块内部该聚的聚。优先组合（composition）而非继承。
- **依赖注入（DI）**：对外部依赖（DB / 网络 / 时钟 / 随机）用参数或接口传入，不硬编码在内部——这是"可测试性"的前提。
- **契约优先（API & Interface Design）**：
  - 先定义接口契约，再写实现；调用双方只依赖契约，不依赖实现。
  - 警惕 **Hyrum 定律**：只要接口有可被观测的行为（哪怕没写进文档），就会有人依赖它。所以契约要显式、边界要收敛。
  - 给契约写"期望与约束"注释（前置/后置条件），而非只写"做什么"。
- **Adapter 隔离边界**：外部系统（第三方 API / 遗留模块）用 Adapter 包一层，内核不认识外部细节。

## 3. 代码坏味道清单（Red Flags，质检层一眼识别）

审查代码时遇到以下信号，直接标记为打回点：

| 坏味道 | 信号 | 处置 |
|---|---|---|
| Long Method / Long Class | 函数/类过长，一屏看不完 | 按「一个函数做一件事」拆 |
| Feature Envy | 一个函数疯狂访问另一个对象的数据来算 | 把逻辑搬进那个对象（Tell-Don't-Ask） |
| Primitive Obsession | 到处用 string/int 裸传业务概念（如 Money 用 number） | 抽领域类型 / 值对象 |
| Shotgun Surgery | 改一个需求要动 N 个文件 | 相关逻辑没收拢（内聚不足） |
| Divergent Change | 一个类因多种不相关原因改 | 违反 SRP，拆 |
| Dead Code | 没被调用的函数 / 没用的变量 | 删（Chesterton's Fence：先确认真无用） |
| Magic Numbers / Strings | 裸字面量散落 | 提为命名常量 |
| Commented-Out Code | 被注释掉的旧代码 | 删，靠 git 历史找 |
| Global State 滥用 | 隐式全局可变状态 | 显式传参 / 收敛边界 |
| 异常吞掉 | `catch` 后空转或无日志 | Fail Fast，至少记录 |

> Chesterton's Fence（切斯特顿栅栏）：删任何代码前先想"当初为何立这栅栏"。确认无用才删，别盲目"简化"。

## 4. 与质量闸门的关系

- 本文件管"**怎么设计 / 怎么写**"；`quality-gates.md` 管"**写好后的量化闸门与打回标准**"。
- 设计时即按第 1、2 节自检；交付时按 `quality-gates.md` 与 `specs/template/verdict.md` 的金线验收表过闸。
- 原则冲突时回到 `constitution.md` 金线三问裁决。
